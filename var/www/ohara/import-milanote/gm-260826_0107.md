### ##🪚 Fix apportés

**_Problème 1 : Titre non affiché_**

- **Symptôme :** Le lecteur restait bloqué sur _"Chargement du titre..."_.

- **Cause :** Nginx ne proxyait pas l’URL `/status-json.xsl` → erreur 404.

- **Solution :** Ajout d’une règle de proxy dans `radio.conf` pour rediriger vers Icecast + headers CORS.

- **Résultat :** Les métadonnées sont accessibles, le titre s’affiche correctement.

- Code modifié : 

`location /status-json.xsl {`

`    proxy_pass http://127.0.0.1:8000/status-json.xsl;`

`    proxy_set_header Host $host;`

`    proxy_set_header X-Real-IP $remote_addr;`

`    add_header 'Access-Control-Allow-Origin' '*' always;`

`    add_header 'Cache-Control' 'no-cache';`

`}`

 

**_Problème 2 : Délai au démarrage audio_**

- **Symptôme :** Long temps d’attente avant lecture du flux.

- **Cause :** Paramètre trop faible (64 Ko) dans `icecast.xml`.

- **Solution :** Augmentation à 256 Ko + redémarrage du service.

- **Résultat :** Buffer rempli instantanément → lecture immédiate.

- Code modifié : 

`<burst-size>262144</burst-size>`

 

**<u>Impact global :</u>**

- Titre des morceaux affiché en temps réel.

- Lecture audio fluide et sans délai

 

**_Problème 3 : Titres_**

- **Synchronisation des titres :** Corrigée en augmentant la fréquence de rafraîchissement de la fonction `fetchCurrentSong` dans `script.js`, assurant une mise à jour plus rapide et plus précise du titre affiché.

- **Formatage des titres :** Réalisé également dans `script.js` pour transformer les noms de fichiers en un format lisible et en majuscules (`ARTISTE - TITRE`).

**Problème 4 :** **Erreur 500**

- Lorsque vous tentiez d'ajouter un nouvel article, le serveur renvoyait une erreur 500. Les logs du serveur ont révélé que le script PHP (`add_post.php`) n'avait pas l'autorisation d'écrire dans le fichier `timeline.json`.

    **Diagnostic :**

    1. Pour des raisons de sécurité, le serveur web (Nginx, Apache) n's'exécute pas en tant que `root`, mais avec un utilisateur aux privilèges limités. Une commande (`ps aux`) a permis d'identifier cet utilisateur comme étant `www-data`.

    2. En inspectant le fichier (`ls -l`), nous avons vu qu'il appartenait à l'utilisateur `root`, et que les "autres" utilisateurs (catégorie dans laquelle `www-data` se trouvait) n'avaient que la permission de lire le fichier, mais pas de le modifier.

    **Solution :** La solution a été de transférer la propriété du fichier `timeline.json` de l'utilisateur `root` à l'utilisateur `www-data`.

    **Commande exécutée sur le serveur :**

    ```bash
    sudo chown www-data:www-data /var/www/html/timeline.json
    
    ```

    Cette action a donné au script PHP, exécuté par `www-data`, la permission d'écrire dans le fichier, ce qui a résolu l'erreur.

### 1. Les branches qui comptent

On a **deux branches importantes** :

- `main` → branche **stable**, “version vitrine”

- `dev` → branche **de travail**, “version en cours”

> Le serveur n’est jamais “magique” :\
> il affiche **la branche sur laquelle il est checkout** (`git checkout`).

---

### 2. Ce que fait un **push sur** `dev`

Quand quelqu’un fait, en local :

```
git checkout dev
git commit ...
git push origin dev

```

👉 Ça déclenche le workflow GitHub **spécial dev**.

Ce workflow fait 3 choses :

1. **Récupérer le code :**

    1. GitHub récupère votre code

    2. Il effectue 2-3 test sur le code (Surtout des erreurs de Syntaxe)

    3. Si les tests sont bons, il passe à la suite.

2. **GitHub se connecter au serveur en SSH**

    1. On s'en fout de comment il fait ça

3. **Sur le serveur, il applique la logique suivante :**

    1. Si le serveur est déjà sur la branche "dev", alors

    2. Il lance un `git pull`  puis relance IceCast2, LiquidSoap et Nginx

    3. Si le serveur est sur une branche qui n'est pas "dev", alors

    4. Il ne lance pas de `git pull` et reste sur la branche actuelle

Donc **en résumé** :

✅ Cas A — Le serveur est sur `dev` 

- Un push sur `dev` :

    - met **à jour le code de la branche dev sur le serveur** (`git pull`),

    - **relance la radio** (Icecast2 + Liquidsoap),

    - met le site à jour avec la dernière version dev.

👉 C’est le mode **“on bosse sur dev en live”**.

---

🛑 Cas B — Le serveur est sur `main`

- Un push sur `dev` :

    - **ne change rien** sur le serveur,

    - pas de `git pull`,

    - pas de `checkout`,

    - pas de restart de services.

👉 Le site reste **en version main**, stable.\
👉 Vous pouvez continuer à bosser sur dev **sans impacter ce que voit le public**.\
\
🛑 Cas C — Le serveur est sur une autre branche (ex : `sandbox`, `feature-x`, etc.)

- Un push sur `dev` :

    - ne fait rien non plus (par sécurité),

    - le script voit que `CURRENT_BRANCH != dev` → il s’arrête.

👉 **Le workflow ne change jamais la branche du serveur tout seul.**

### 1️⃣ Récupérer la dernière version

Toujours commencer par mettre ton dépôt local à jour avec ce qu’il y a sur le serveur.

- `git pull origin main` → récupère et fusionne les changements de la branche principale.

 

- 👉 Évite les conflits en travaillant sur la version la plus récente.

 

### 2️⃣ Créer ou basculer sur une branche

Ne jamais travailler directement sur `main`.

- `git branch `→ créer une nouvelle branche (ex : `feature-radio`).

- `git switch `→ basculer dessus.

- 👉 Chaque fonctionnalité ou correction doit avoir sa propre branche.

 

### 3️⃣ Travailler et suivre les fichiers

Pendant que tu modifies ton code :

- `git status` → voir quels fichiers ont changé.

- `git add `→ préparer un fichier pour le commit.

- `git add .` → préparer tous les fichiers modifiés.

 

### 4️⃣ Enregistrer ton travail (commit)

Quand tu as fini une étape claire :

- `git commit -m "Explication du changement"` → sauvegarde locale avec explication.

- 👉 Un commit = une petite avancée (pas tout un projet d’un coup).

 

### 5️⃣ Partager ton travail (push)

Quand ta branche contient des commits prêts à être vus par les autres :

- `git push origin `→ envoie tes commits sur le dépôt distant.

- 👉 Tes collègues peuvent maintenant voir et tester ton travail.

 

### 6️⃣ Fusionner dans la branche principale

Quand ta fonctionnalité est validée :

- `git checkout main` → revenir sur la branche principale.

- `git pull origin main` → s’assurer d’avoir la dernière version.

- `git merge `→ fusionner ta branche dans `main`.

- `git push origin main` → publier la nouvelle version principale.

 

### 7️⃣ Nettoyer

- `git branch -d `→ supprimer une branche locale une fois fusionnée.

- 👉 Garde ton projet propre et lisible.

 

### 📌 Résumé :

 

1. **Pull** → mets ton projet à jour.

2. **Branch** → crée une piste de travail.

3. **Add + Commit** → enregistre tes changements.

4. **Push** → partage ta branche.

5. **Merge** → intègre dans `main`.

6. **Push main** → publie la version finale.
